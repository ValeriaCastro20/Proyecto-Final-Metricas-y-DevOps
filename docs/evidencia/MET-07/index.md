# MET-07: Análisis de Degradación Inducida y Recuperación

## 1. Hipótesis
Si se reduce a cero la capacidad del componente procesador (`process`) en un entorno de prueba mientras el sistema recibe una carga sostenida de eventos, el servicio de ingesta (`serve`) seguirá aceptando peticiones y devolviendo `202 Accepted` sin interrupción (debido al diseño de inbox transaccional). Como comportamiento esperado de los requisitos de observabilidad pendientes de integrar (`MET-02` a `MET-06`), el indicador de backlog (`esc3_events_backlog_total`) crecerá de forma lineal hasta disparar la alerta `HighEventBacklog`. Al restaurar el procesador, el backlog debe drenarse sin pérdida de datos.

## 2. Procedimiento y Secuencia Temporal
* **T0 (Estado Normal):** El sistema opera con normalidad en el entorno de prueba. API y Procesador activos. Se espera que `esc3_events_backlog_total` se mantenga cercano a `0`.
* **T1 (Inyección de Carga):** Se inicia el script de simulación generando tráfico de eventos de manera sostenida durante 2 minutos y registrando todos los intentos enviados junto con el `reading_id` de cada respuesta `202 Accepted`.
* **T2 (Degradación Inducida):** Se detiene intencionalmente únicamente un worker de `process` autorizado en el entorno de prueba aislado (esta prueba no se realiza en ningún entorno compartido sin autorización).
* **T3 (Detección - Síntoma Operativo):** 
  * **Resultado observado (API y Base de Datos):** La recepción en `/v1/readings` continúa insertando lecturas en PostgreSQL cuyas filas permanecen con `processed_at IS NULL`.
  * **Comportamiento esperado (requisitos de observabilidad pendientes):** `esc3_events_backlog_total` y `HighEventBacklog` constituyen requisitos de observabilidad aún pendientes de integración en `main` (no señales ya verificadas en esta rama). Una vez integrados, el resultado esperado es que la latencia HTTP (`http_request_duration_seconds`) se mantenga estable, el contador `esc3_events_received_total` suba a ritmo constante y el gauge `esc3_events_backlog_total` supere el umbral crítico de `> 100` eventos pendientes durante un plazo de `2m`, disparando la alerta `HighEventBacklog` con severidad `critical`.
* **T4 (Respuesta/Recuperación):** Se vuelve a levantar el worker de prueba del componente `process`.
* **T5 (Resolución):** El procesador arranca y consume los lotes pendientes de la base de datos. Para verificar la ausencia de pérdida de datos, se toman todos los `reading_id` registrados en cada respuesta `202 Accepted` y se comprueba en PostgreSQL que todos ellos aparecen entre las lecturas con `processed_at` establecido (`processed_at IS NOT NULL`). De manera complementaria (sin usar estas señales como sustituto de la verificación por `reading_id`), se observa como comportamiento esperado que `esc3_events_backlog_total` disminuya a `0` y que la alerta `HighEventBacklog` se resuelva automáticamente en Grafana.

## 3. Interpretación de Señales Correlacionadas (Logs y Trazas)
Para evaluar el aislamiento entre la ingesta y el procesador durante la ventana `T2–T4`, se contrastan el total de intentos enviados por el cliente frente a las respuestas `202 Accepted`, los rechazos `422 Unprocessable Entity` y los posibles fallos de conexión o errores `5xx`. Se afirma que la ingesta continuó sin interrupciones únicamente si esa evidencia confirma que todos los intentos enviados recibieron la respuesta `202` o `422` esperada con cero errores `5xx` y cero fallos de conexión; en caso contrario, la conclusión se ajusta indicando degradación parcial durante el incidente. De forma correlacionada, en las trazas de OpenTelemetry (Jaeger) y logs estructurados (requisitos de `MET-02`–`MET-04`) se espera observar _spans_ de `/v1/readings` sin su ejecución inmediata de procesamiento durante `T2–T4` y ausencia de errores `500`.

## 4. Limitaciones del Experimento
Este experimento valida el desacoplamiento lógico entre la recepción y el procesamiento, pero asume que la base de datos (PostgreSQL) y el ancho de banda de red tienen capacidad adecuada. Si el apagón del procesador se prolonga de forma indefinida, el almacenamiento de la base de datos podría verse comprometido, provocando eventualmente una saturación en cascada.
