# MET-07: Análisis de Degradación Inducida y Recuperación

## 1. Hipótesis
Si se reduce a cero la capacidad del componente procesador (`process`) en un entorno de prueba aislado mientras el servicio de ingesta (`serve`) recibe una carga sostenida de eventos, el servicio de ingesta seguirá aceptando peticiones válidas (`202 Accepted` para lecturas nuevas y `200 OK` para retransmisiones idempotentes) sin interrupción gracias al diseño de inbox transaccional. Como comportamiento esperado de los requisitos de observabilidad pendientes de integrar (`MET-02` a `MET-06`), el indicador de backlog (`esc3_events_backlog_total`) crecerá de forma lineal hasta disparar la alerta `HighEventBacklog`. Al restaurar el procesador, el backlog debe drenarse sin pérdida de datos.

## 2. Procedimiento y Secuencia Temporal
* **T0 (Estado Normal y Precondición):** El sistema opera en el entorno de prueba aislado y autorizado con API y Procesador activos dentro del namespace de prueba verificado (`NS`). Antes de ejecutar `T2`, se confirma el contexto del clúster (`kubectl config current-context`) y se verifica en `"$NS"` que haya **exactamente un worker activo** de `process` (`kubectl -n "$NS" get deployment/event-service-worker`); si hay más de uno, no se realiza la prueba hasta que se cumpla esa condición. Se espera que `esc3_events_backlog_total` se mantenga cercano a `0`.
* **T1 (Inyección de Carga):** Se inicia el script de simulación generando tráfico de eventos de manera sostenida durante 2 minutos, registrando por separado cada intento enviado, el código de estado recibido (`202`, `200`, `422`, `5xx` o fallo de conexión) y el `reading_id` devuelto en las respuestas `202 Accepted` y `200 OK`.
* **T2 (Degradación Inducida):** Únicamente en el entorno de prueba aislado y autorizado (nunca en un entorno compartido sin autorización), tras confirmar el contexto activo del clúster (`kubectl config current-context`) y verificar que en el namespace `"$NS"` solo existe un worker activo de `process`, se escala explícitamente `event-service-worker` a cero réplicas en dicho namespace (`kubectl -n "$NS" scale deployment/event-service-worker --replicas=0`) y se espera a que el Pod termine por completo (`kubectl -n "$NS" wait --for=delete pod -l app=event-service-worker --timeout=60s`) antes de continuar para garantizar que la capacidad de procesamiento permanezca en cero durante `T2–T4`.
* **T3 (Detección - Síntoma Operativo Esperado):** 
  * **Resultado esperado en API y Base de Datos (diseño experimental previo a ejecución):** Mientras `event-service-worker` se mantiene en cero réplicas durante `T2–T4`, se espera que la recepción en `/v1/readings` continúe registrando nuevas lecturas en PostgreSQL cuyas filas permanezcan en estado pendiente (`processed_at IS NULL`).
  * **Comportamiento esperado en observabilidad (requisitos pendientes):** `esc3_events_backlog_total` y `HighEventBacklog` constituyen requisitos de observabilidad pendientes de integración en `main` (no señales ya disponibles ni verificadas en esta rama). Una vez integrados, el resultado esperado es que la latencia HTTP (`http_request_duration_seconds`) se mantenga estable, el contador `esc3_events_received_total` suba a ritmo constante y el gauge `esc3_events_backlog_total` supere el umbral crítico esperado de `> 100` eventos pendientes durante un plazo de `2m`, disparando la alerta `HighEventBacklog` con severidad `critical`.
* **T4 (Respuesta/Recuperación):** Se mantiene la capacidad del worker en cero y se espera hasta que haya **más de 100 lecturas pendientes durante dos minutos (`2m`)** antes de volver a levantar el worker de prueba del componente `process`. Cumplida esa condición dentro del entorno de prueba aislado y autorizado, y habiendo confirmado el contexto del clúster, se restaura `event-service-worker` en el namespace verificado `"$NS"` al número de réplicas que tenía antes de la prueba (`kubectl -n "$NS" scale deployment/event-service-worker --replicas=1`).
* **T5 (Resolución):** El procesador arranca y consume los lotes pendientes de la base de datos. Para verificar la ausencia de pérdida de datos, se registran todos los `reading_id` de cada respuesta `202 Accepted` (y los confirmados en retransmisiones `200 OK`) y se comprueba en PostgreSQL que todos aparecen entre las lecturas con `processed_at` establecido (`processed_at IS NOT NULL`). De manera complementaria (sin usar estas señales como sustituto de la verificación de ausencia de pérdida por `reading_id`), se espera observar que el backlog (`esc3_events_backlog_total`) disminuya a `0` y que la alerta `HighEventBacklog` se resuelva automáticamente en Grafana.

## 3. Interpretación de Señales Correlacionadas (Logs y Trazas)
Para evaluar el aislamiento de la ingesta durante `T2–T4`, se contrastan los intentos enviados por el cliente registrando y evaluando por separado:
1. **Respuestas `202 Accepted` de nuevas solicitudes:** Lecturas válidas ingresadas por primera vez con su `reading_id`.
2. **Respuestas `200 OK` de retransmisiones válidas:** Reintentos idempotentes que devuelven `200 OK` conservando el `reading_id` original; este resultado se trata como **respuesta esperada** del contrato de ingesta y no como degradación.
3. **Rechazos `422 Unprocessable Entity`:** Solicitudes inválidas rechazadas de forma controlada con su recibo correspondiente.
4. **Errores `5xx` y fallos de conexión:** Fallos reales de disponibilidad o capacidad en la ingesta.

Se afirma que la ingesta continuó sin interrupciones únicamente si esa evidencia confirma que todos los intentos enviados durante `T2–T4` recibieron respuestas esperadas (`202` para nuevas solicitudes, `200` con el `reading_id` original para retransmisiones válidas o `422` para rechazos de validación), con cero errores `5xx` y cero fallos de conexión; en caso contrario, se ajusta la conclusión reflejando degradación. De forma correlacionada, como comportamiento esperado de las trazas de OpenTelemetry (Jaeger) y logs estructurados (requisitos pendientes `MET-02`–`MET-04`), durante `T2–T4` se espera observar _spans_ de `/v1/readings` sin procesamiento inmediato y ausencia de errores `500`.

## 4. Limitaciones del Experimento
Este experimento valida el desacoplamiento lógico entre la recepción y el procesamiento, pero asume que la base de datos (PostgreSQL) y el ancho de banda de red tienen capacidad adecuada. Si el apagón del procesador se prolonga de forma indefinida, el almacenamiento de la base de datos podría verse comprometido, provocando eventualmente una saturación en cascada.
